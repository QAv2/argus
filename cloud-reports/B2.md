## How the project builds and runs

This was not written down anywhere. There is no README or CLAUDE.md. What I worked out:

- **Static site, no build step.** `index.html` loads CesiumJS 1.136 and satellite.js 5.0.0 from CDNs, then 21 plain scripts from `js/` (no bundler, no modules). The data comes from `data/*.json` and `data/theaters/*.json`.
- **Netlify.** `netlify.toml` publishes the repo root (`publish = "."`). The build command is `echo 'Build complete'` and the Node version is 20. There are three functions in `netlify/functions/`:
  - `config.js` serves `MAPTILER_API_KEY` and `CARTO_API_KEY` from env vars at runtime.
  - `proxy.js` is a CORS proxy, allowlisted to CelesTrak, adsb.lol and one GitHub raw path.
  - `vessels.js` collects AIS data server-side from aisstream.io using `ws` and `AISSTREAM_API_KEY`.
- **Run locally.** Run `python3 -m http.server 8080` (or `npm run dev`) in the repo root and open http://127.0.0.1:8080/. Without `netlify dev` the three functions return 404, so aircraft, vessels, satellites and the keyed basemaps don't load. Everything under `data/` still loads, and so do the USGS quakes, GDACS and the intel-console feed (`https://qav2.github.io/intel-console/data`).
- **Live sources** the page fetches directly: USGS earthquakes, GDACS and the intel-console GitHub Pages feed. Sources that go through the functions: CelesTrak, adsb.lol and aisstream.io.
- **Sweep tooling** lives in `tools/sweep/` and has its own README. It covers merging and validating new theater and disaster events, building the briefing page, a vm-sandbox test of `js/disasters.js`, and a headless-Chrome boot check (`cdp_smoke.js`). The `inbox/` input folder is gitignored and does not exist in a fresh clone.
- **Capture daemon** lives in `capture/`. It is Python (aiohttp, aiosqlite) and runs as a systemd service on a VM, installed by `capture/deploy.sh` into `/opt/argus`.
- **One-off scripts:** `scripts/generate-roads.js` and `scripts/merge_comnap.py` regenerate files in `data/`. I did not run them, because they write to `data/`.

New in this PR:

```
npm ci
npm test          # static check + disasters harness, no network or browser needed
python3 -m http.server 8080 &
npm run smoke     # headless boot check, needs google-chrome or CHROME_BIN=/path/to/chromium
```

## What I fixed

Commits, oldest first:

1. **`534549d` Bump ws 8.19.0 → 8.22.0.** This clears two high-severity advisories (memory disclosure, and DoS via tiny fragments). It is a minor bump within `^8`, and I raised the floor in `package.json` to `^8.22.0`. `ws` is used only by `netlify/functions/vessels.js` and `tools/sweep/cdp_smoke.js`. I checked that the function still loads and responds, and the boot smoke still connects over CDP with the new version.
2. **`4138049` `capture/sentinel.service` paths.** The unit still used `/opt/worldview` from before the WORLDVIEW → ARGUS rebrand, while `deploy.sh` clones to and builds the venv in `/opt/argus`. A fresh deploy would have failed to start the service. I changed the three paths and the description.
3. **`f218691` Safety net.** Adds `tools/check_static.js`, which has no dependencies and needs no network. It fails when:
   - `index.html` references a missing local file,
   - a front-end or function JS file stops parsing,
   - a literal `data/…json` path in `js/` is missing,
   - a theater listed in `js/conflicts.js` has no data file,
   - or a core data file is invalid JSON or empty.

   It also wires up `npm test` and adds `.github/workflows/test.yml`, which runs `npm ci && npm test` on PRs and on pushes to `master`.
4. **`6a18012` Sweep harnesses fail on bad output.** Before this commit, `test_disasters.js` and `cdp_smoke.js` printed results and exited 0 unless they crashed.
   - `test_disasters.js` now exits 1 if no curated events or entities load, or if any entity has bad lat/lon/name.
   - `cdp_smoke.js` now exits 1 if boot doesn't reach `SYSTEMS ONLINE` or if any of the local-data layers (conflicts, disasters, antarctica, military) is empty.
   - `CHROME_BIN` overrides the hard-coded `google-chrome`, and `npm run smoke` wraps the boot check. The sweep README is updated to match.

## Secrets and privacy check

Method: I grepped the working tree (`git grep`) and the full history of all branches (`git log --all -p`) for:

- AWS, Google, OpenAI, GitHub and Slack key patterns, JWTs and private-key blocks,
- `api_key|token|secret|password = "<long string>"`,
- `?key=` / `?token=` in URLs,
- e-mail addresses, home-directory paths and phone numbers,
- and any file ever added that matches `.env`, `.key`, `.pem`, `secret`, `credential`, `token`, `.db` or `captures/`.

Findings:

- **No keys or tokens.** The only key-like strings in history are the placeholder `'__MAPTILER_API_KEY__'` and `Cesium.Ion.defaultAccessToken = undefined`. Keys are served at runtime from Netlify env vars by `netlify/functions/config.js`, which reads `process.env` and holds no literals.
- **No `.env`, key, pem or capture database files** were ever committed. `.gitignore` covers `.env`, `*.key`, `*.pem` and `data/captures/`.
- **E-mail:** the only addresses are commit metadata, `contact@qualia-algebra.com` (author on all 50 commits) and `noreply@anthropic.com` (co-author lines). None appear in file contents.
- **No personal paths or phone numbers.** There are `~/` references in docs (`CINEMA_MODE.md`, `tools/sweep/README.md`, `merge_sweep.py` docstring), but none contain a username.

I did not run GitHub's own secret scanning.

## What's left / needs a decision from Joe

**Majors and runtime bumps (listed, not done):**

- **satellite.js 5.0.0 → 7.1.0** (CDN, `index.html`). Two majors behind. Used by `js/satellites.js` and `js/sat-correlation.js` for SGP4 propagation. It needs an API check before bumping.

**Optional minor (not security-driven, not done):**

- **CesiumJS 1.136 → 1.146** (CDN). Cesium versions are all 1.x, but releases do change behaviour. I found no advisory that applies, so I left it.

**Other observations, no change made:**

- `capture/requirements.txt` lists `Pillow` and `sgp4`, but no code in `capture/` imports them. Also, `deploy.sh` installs only `aiohttp aiosqlite` and ignores the requirements file. That's harmless, but the two disagree.
